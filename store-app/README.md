# تطبيق إدارة المحل (Store App)

تطبيق فلاتر (Flutter) لإدارة محل صغير أو متوسط، بنفس الكود لكل من **ويندوز** و**أندرويد** و**متصفح الويب**. البيانات كلها مركزية على مشروع [Supabase](https://supabase.com) واحد — فأي تغيير (بيع، دين، منتج جديد...) يظهر فوراً على كل الأجهزة المتصلة بنفس المشروع.

## المزايا

- **تسجيل دخول لكل موظف**: كل موظف له رمز دخول (code) وكلمة مرور خاصة به، ويُضاف من شاشة الإعدادات من قبل المدير فقط. كلمات المرور مُشفّرة، ولا تُرسل أبداً لأي جهاز — تبقى داخل قاعدة البيانات فقط.
- **صلاحيات**: حساب "مدير" يرى كل الشاشات بما فيها الإعدادات، وحساب "كاشير" يرى المنتجات/المبيعات/الديون/التقارير فقط، وهذا مفروض من الخادم نفسه وليس فقط من واجهة التطبيق.
- **المنتجات**: إضافة/تعديل/حذف، مع سعر الشراء والبيع والكمية ووحدة القياس، وتنبيه عند اقتراب نفاد المخزون. البحث والقوائم مقسّمة على صفحات (تحميل المزيد) بحيث تبقى سريعة حتى مع آلاف المنتجات.
- **المبيعات**: نقطة بيع بسيطة (سلة مشتريات)، تدعم الدفع الكامل أو الجزئي — أي مبلغ غير مدفوع يتحول تلقائياً لدين على اسم الزبون، مع خصم الكمية من المخزون تلقائياً وبشكل آمن حتى لو باع جهازان نفس المنتج بنفس اللحظة (لا يمكن أن تنزل الكمية تحت الصفر)، وسجل لكل عمليات البيع.
- **الديون**: قائمة بكل الزبائن الذين عليهم ديون، مع إمكانية إضافة دين يدوي أو تسجيل دفعة، وسجل حركات كامل لكل زبون.
- **التقارير والأرباح**: إجمالي المبيعات وصافي الربح (حسب اليوم/الأسبوع/الشهر/الكل)، أكثر المنتجات مبيعاً، وتنبيهات نفاد المخزون — كلها محسوبة داخل قاعدة البيانات مباشرة (سريعة حتى مع بيانات كبيرة).
- **الإعدادات**: إدارة الموظفين (إضافة/تعديل/تعطيل/حذف)، تحديد الصلاحية، وتغيير كلمة المرور.
- **تحديث مباشر (Realtime)**: شاشات المنتجات والمبيعات والديون تتحدث تلقائياً عند حدوث تغيير من جهاز آخر، بدون حاجة لإعادة فتح الشاشة.

## هيكلة المشروع

```
supabase/schema.sql   قاعدة البيانات الكاملة (جداول + صلاحيات + دوال) — تُشغَّل مرة واحدة في مشروع Supabase
lib/
  config/    supabase_config.dart — رابط ومفتاح مشروع Supabase الخاص بك
  models/    نماذج البيانات (موظف، منتج، عملية بيع، زبون، حركة دين)
  services/  backend_service.dart — كل التواصل مع Supabase (قراءة/كتابة/دوال/تحديث مباشر)
  state/     session.dart — حالة تسجيل الدخول الحالية
  screens/   شاشات التطبيق (إعداد أول مرة، دخول، منتجات، مبيعات، ديون، تقارير، إعدادات)
```

## 1) إعداد مشروع Supabase (مرة واحدة)

1. أنشئ حساباً مجانياً على [supabase.com](https://supabase.com) ثم أنشئ مشروعاً جديداً (اختر كلمة مرور قوية لقاعدة البيانات واحتفظ بها).
2. من لوحة التحكم: **SQL Editor** → **New query** → الصق محتوى ملف `supabase/schema.sql` بالكامل → **Run**. هذا ينشئ كل الجداول وقواعد الصلاحيات والدوال.
3. من **Authentication → Providers → Anonymous Sign-Ins**: فعّلها (هذا الإعداد الوحيد غير الممكن عبر SQL — التطبيق يسجّل دخول كل جهاز بشكل مجهول تلقائياً حتى يستطيع القراءة والكتابة ضمن قواعد الصلاحيات).
4. من **Project Settings → API**: انسخ **Project URL** و**anon public key** (مفتاح anon مخصص للاستخدام داخل التطبيقات، وهو آمن للتضمين في الكود لأن كل الجداول محمية بقواعد RLS في `schema.sql`).

## 2) ربط التطبيق بالمشروع

افتح `lib/config/supabase_config.dart` وضع القيمتين مباشرة:

```dart
static const url = String.fromEnvironment('SUPABASE_URL', defaultValue: 'https://xxxx.supabase.co');
static const anonKey = String.fromEnvironment('SUPABASE_ANON_KEY', defaultValue: 'eyJ...');
```

أو بدون تعديل الكود، مرّرهما وقت التشغيل/البناء:

```bash
flutter run --dart-define=SUPABASE_URL=https://xxxx.supabase.co --dart-define=SUPABASE_ANON_KEY=eyJ...
```

عند أول فتح للتطبيق على مشروع جديد (لا يوجد أي موظف بعد) ستظهر شاشة **"إعداد المحل لأول مرة"** لإنشاء حساب المدير الأول مباشرة من التطبيق — لا حاجة لإنشائه يدوياً في قاعدة البيانات.

## متطلبات التشغيل

- [Flutter SDK](https://docs.flutter.dev/get-started/install) (قناة stable).
- لبناء أندرويد: Android Studio SDK/تجهيزات أندرويد (`flutter doctor` يوضح الناقص).
- لبناء ويندوز: يجب التنفيذ من جهاز ويندوز فيه Visual Studio (Desktop development with C++) مُثبّت.
- لا شيء إضافي لتشغيله كصفحة ويب — يكفي متصفح حديث.

## التشغيل والتطوير

```bash
cd store-app
flutter pub get
flutter run            # يشغل التطبيق على أي جهاز/محاكي متصل
flutter run -d chrome   # لتشغيله كصفحة ويب أثناء التطوير
```

## البناء للإصدار النهائي

### أندرويد (APK)

```bash
flutter build apk --release
# الناتج: build/app/outputs/flutter-apk/app-release.apk
```

### ويندوز (تنفيذ من جهاز ويندوز)

```powershell
flutter build windows --release
# الناتج: build\windows\x64\runner\Release\
```

انسخ محتويات مجلد `Release` كاملاً (وليس فقط ملف exe) لتوزيع التطبيق على أجهزة ويندوز أخرى.

### صفحة الويب

```bash
flutter build web --release
# الناتج: build/web — ارفع محتوياته لأي استضافة ثابتة (Netlify, Vercel, GitHub Pages, أو استضافة Supabase نفسها)
```

الأجهزة الثلاثة تتصل بنفس مشروع Supabase، فأي عملية بيع أو تعديل منتج على جهاز يظهر فوراً على البقية.

## الاختبار والتحقق

- `flutter analyze` و`flutter test`: تم تشغيلهما وخرجا نظيفين بدون أخطاء.
- **قاعدة البيانات (`supabase/schema.sql`)**: تم التحقق من كل دالة وقاعدة فيها فعلياً على نسخة PostgreSQL محلية (وليس فقط بمراجعة الكود) — تسجيل الدخول بكود صحيح/خاطئ، رفض تكرار رمز الموظف، منع الكاشير من إدارة الموظفين، منع حذف آخر مدير، منع بيع كمية أكبر من المتوفر مع بقاء المخزون كما هو عند الفشل، احتساب الدين والربح والتقارير بأرقام صحيحة، ومنع الوصول لجدول الموظفين مباشرة حتى بمفتاح anon. كما تم اختبار حالة تزامن حقيقية: جهازان يحاولان بيع نفس آخر كمية متبقية بنفس اللحظة — العملية الأولى نجحت والثانية رُفضت تلقائياً بدون نقصان المخزون تحت الصفر.
- **تطبيق فلاتر نفسه**: لم يُختبر بالتشغيل الفعلي ضد مشروع Supabase حقيقي داخل بيئة التطوير هذه، لأن سياسة الشبكة هنا تمنع الوصول لصور Docker اللازمة لتشغيل نسخة Supabase محلية، ولا تتوفر بيانات دخول لمشروعك الحقيقي. بعد إكمال خطوة "1) إعداد مشروع Supabase" أعلاه، شغّل اختبار التكامل للتحقق من التطبيق كاملاً بنفس الطريقة:

```bash
flutter test integration_test/app_test.dart -d windows \
  --dart-define=SUPABASE_URL=https://xxxx.supabase.co \
  --dart-define=SUPABASE_ANON_KEY=eyJ...
```

(استخدم مشروع Supabase تجريبي وليس مشروعك الحقيقي، لأن الاختبار ينشئ بيانات فعلية.)

## ملاحظات أمنية

- جدول `employees` غير قابل للوصول مباشرة إطلاقاً (لا حتى بالقراءة) — كل عمليات الموظفين تمر عبر دوال محمية في قاعدة البيانات.
- كل الأجهزة تستخدم "دخول مجهول" (anonymous) واحد لتحقيق شرط "دخول موثّق" الذي تتطلبه قواعد الصلاحيات، وهذا يمنع استخدام مفتاح anon وحده من خارج التطبيق لسحب البيانات مباشرة. هذا مستوى حماية معقول لمحل صغير/متوسط؛ لو احتجت حماية أقوى مستقبلاً (حسابات Supabase حقيقية لكل موظف، صلاحيات على مستوى قاعدة البيانات لكل حساب) يمكن تطويره لاحقاً.
